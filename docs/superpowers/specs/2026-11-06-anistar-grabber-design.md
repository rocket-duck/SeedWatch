# Кастомный граббер AniStar для SeedWatch

Дата: 2026-11-06
Статус: дизайн на утверждении

## Намерение и зачем

Сайт [anistar.org](https://anistar.org/) выкладывает торренты сериалов (в основном
аниме) по мере выхода серий. Готового индексера для него нет ни в Prowlarr, ни в
Jackett. Пользователь хочет, чтобы новые серии с этого сайта автоматически
попадали в его конвейер загрузки.

Модель сайта отличается от RuTracker: нет «раздачи, которая разрастается» —
вместо этого у каждого сериала есть **страница сериала** со списком торрентов,
где **каждая серия — отдельный .torrent**.

Результат: SeedWatch научится отслеживать страницы сериалов с AniStar напрямую,
минуя Prowlarr, и отправлять новые серии в qBittorrent через свой существующий
`QbitClient`.

## Разведка сайта (выполнена, spike 2026-11-06)

Файлы spike: `/tmp/anistar_spike.py` (throwaway, в проект не идёт).

Установлено:

- Доступ: Cloudflare фильтрует только по User-Agent. UA
  `Mozilla/5.0 (compatible; ReleaseMonitor/1.0)`, который SeedWatch уже шлёт,
  проходит (HTTP 200 на страницу и на скачивание). FlareSolverr и логин **не
  нужны**.
- Страница сериала — список блоков `div.torrent` (`id="torrent_<id>_info"`),
  каждый содержит подпись вида `Серия 91 (758.31 Mb)`, ссылку
  `/engine/gettorrent.php?id=<id>`, сидов и дату `Дата: 29-10-2026`.
  Кодировка страниц windows-1251.
- `.torrent` отдаётся без логина (`application/x-bittorrent`), анонсер
  `http://t.anistar.org:2710/announce` **без passkey** — рейтинг-фри, безопасно
  для автоматизации.
- Дубликаты: одна серия может иметь несколько торрентов. Подписи
  дубликатов (проверено на реальных страницах): `Серия 14` и
  `Серия 14 Многоголосая озвучка`; `Серия 93 [Xelenum]` и
  `Серия 93 [Xelenum & Sati Akura]` — то есть комментарий (озвучка, группа)
  идёт в подписи сразу после номера серии. Вывод: отслеживать по
  `torrent_id`, не по номеру серии; при выборе на серию отдавать приоритет
  подписи с «многоголосой» озвучкой.
- Встречаются дробные серии: `Серия 240.5` — целый номер не извлекается,
  такой торрент учитывается, но не грабится (`episode=None`).
- RSS сайта (`/rss.xml`) — лента новостей сериалов, не новых серий. Для задачи
  бесполезен.
- У сайта есть зеркала (в RSS встречается `v2.astar.bz`). Парсер должен
  следовать редиректам и распознавать зеркала.
- Разбор проверен на шести страницах (31–247 торрентов на страницу), включая
  четыре дополнительных по запросу владельца (Douluo Dalu, Swallowed Star,
  Shrouding the Heavens, Doupo Cangqiong 5): стабилен, дубликаты корректно
  извлекаются.

## Цели

- Пользователь вставляет в SeedWatch ссылку на страницу сериала с AniStar —
  сервис начинает отслеживать появление новых серий.
- Новая серия (новый `torrent_id` на странице) автоматически скачивается
  `.torrent`-файлом и отправляется в qBittorrent.
- **Режим догона**: если при добавлении сериал в Sonarr привязан, но в нём ещё
  нет ни одного скачанного эпизода — скачиваются все серии, что есть на
  странице. Если в Sonarr уже что-то есть — только новые серии по мере выхода
  (текущая логика).
- При привязке к сериалу Sonarr уже скачанные серии пропускаются (проверка
  `hasFile`, существующий код).
- История срабатываний, пауза, ручная проверка, интервал — работают как для
  обычных раздач.

## Не-цели

- Индексер для Prowlarr (Torznab-прокси) — отдельная история, если понадобится.
- «Догон» при частично заполненной библиотеке Sonarr (есть серии 1–50, на
  странице 1–91): существующие серии не грабятся, только будущие. Догон
  частичной библиотеки — задача Sonarr.
- Поддержка нескольких озвучек на серию сверх выбора «один торрент на серию»
  с приоритетом (см. «Дубликаты»).
- FlareSolverr-фолбэк для AniStar: защита сейчас слабая; если усилят —
  отдельная доработка (архитектурно место предусмотрено).

## Анти-цели

- Не сломать существующий поток через Prowlarr: раздачи с `source='prowlarr'`
  обрабатываются ровно как сейчас.
- Не делать массовую отправку неосознанной: режим догона (все серии разом)
  включается только при пустой библиотеке Sonarr. Случайный масс-граб от
  смены вёрстки/зеркала блокируется порогом новизны (см. ниже).
- Не молчать при смене вёрстки: если страница прочиталась, но торрентов не
  нашлось — это ошибка, а не «без изменений».

## Подходы (рассмотренные)

- **A. Прямая интеграция в SeedWatch** — выбран. Новый источник раздачи; парсер
  в новом модуле; отправка в qBittorrent существующим клиентом. Плюсы: ноль
  новых сервисов, переиспользование конвейера (Sonarr, история, расписание).
  Минусы: привязка к сайту в коде SeedWatch.
- **B. Torznab-прокси → Prowlarr.** Отдельный микро-сервис-индексер; SeedWatch
  не меняется. Отклонён: лишний контейнер, качество поиска зависело бы от
  встроенного поиска DLE, а задача — мониторинг страниц, а не поиск.
- **C. Cardigann YAML в Prowlarr/Jackett.** Отклонён: модель сайта
  «страница сериала со списком торрентов» плохо выражается в Cardigann.

## Решения по реализации

### Распознавание источника

По хосту URL: `anistar.org` и `*.astar.bz` (суффикс, покрывает `v2.astar.bz`
и будущие поддомены) → `source='anistar'`, иначе `source='prowlarr'`.
Список — одна константа `ANISTAR_HOST_SUFFIXES` в `app/anistar.py`
(авторитетный источник); в `app.js` продублирован минимальный список для
мгновенного переключения формы до отправки. (Моё решение; обоснование: UX
формы не меняется, ошибок выбора нет. Если сайт сменит домен — правка одной
константы.)

Предположение: зеркала — одна база DLE, `torrent_id` переносим между ними.
Страховка от ошибочного предположения: **порог новизны** — если за одну
проверку появилось больше 15 **ранее невиданных** id, ничего не грабить,
перевести раздачу в `error` с сообщением «подозрительно много новых торрентов
(N)». Порог не распространяется на режим догона (там массовая отправка
осознанная). Это же защищает от смены вёрстки, при которой парсер начинает
выдумывать id.

### Схема данных

Таблица `releases`, новые колонки (через миграцию в `Store.init`, как
существующие `sonarr_*`):

- `source TEXT NOT NULL DEFAULT 'prowlarr'`;
- `known_torrents TEXT NOT NULL DEFAULT '[]'` — JSON-массив объектов
  `{"id": int, "episode": int|null, "processed": bool, "grabbed": bool}`.
  Семантика: `processed` — id обработан (отправлен, пропущен как скачанный,
  проиграл дедупликацию, либо взят в baseline); только не-`processed` id
  рассматриваются как кандидаты. `grabbed` — был реально отправлен в
  qBittorrent (для истории/отображения).

Для anistar-раздач: `url` = URL страницы сериала, `topic_id` = числовой id
сериала из URL (`/8883-slug.html` → `8883`), `title` = заголовок страницы
сериала, `episodes` = отсортированные номера серий (как сейчас, для отображения).

### Кандидаты на граб и выбор торрента на серию

Единая логика для добавления и проверки:

1. Кандидаты = торренты страницы с `processed=false` (новые id + ранее
   неудачные попытки) — и, **только если задан `sonarr_series_id` и в Sonarr
   нет ни одного скачанного эпизода**, — все остальные торренты страницы
   тоже (режим догона).
2. Среди кандидатов отбрасываются `episode=None` (дробные серии вроде
   «240.5», нестандартные подписи): помечаются `processed`, не грабятся.
3. Дедупликация по серии: на одну серию — один торрент. Выбор:
   1. подпись содержит «многоголос» (регистронезависимо) — высший приоритет;
   2. иначе — наибольшее число сидов (при равенстве — свежий по дате).
   Проигравшие дедупликацию помечаются `processed` без отправки.
4. Если Sonarr привязан и его библиотека не пуста — серии кандидатов,
   уже скачанные в Sonarr, пропускаются с записью в историю.

(Правило приоритета «многоголос» — требование владельца; сиды как
вторичный критерий — моё решение.)

### Добавление раздачи (`Monitor.add_release`)

Ветка по `source`:

1. Скачать страницу (обычный `self.http`, редиректы следуют; если настроен
   FlareSolverr — через него, по аналогии с `fetch_topic_title`, архитектурно
   фолбэк уже на месте).
2. Разобрать: заголовок сериала + список торрентов.
3. Создать запись: `known_torrents` пустой, `episodes` = все распознанные
   номера серий, статус `monitoring`.
4. Если задан `sonarr_series_id` и скачанных эпизодов в Sonarr нет —
   **режим догона**: все серии страницы отправляются в qBittorrent (через
   общую логику кандидатов). Это долгая операция (~200 торрентов при первом
   добавлении), UI уже ждёт до 300 с.
5. Иначе (Sonarr не привязан или в нём уже что-то есть): все текущие id
   помечаются `processed` (baseline), **ничего не грабить**. (Моё решение:
   без привязки к Sonarr массовый граб при добавлении не делаем — нет
   защиты от заливки всего сайта по одной ссылке; мониторинг новых серий
   работает сразу.)
6. Сообщение пользователю: «Сериал добавлен, отслеживается N серий» (+ при
   догоне: «, отправлено M серий в qBittorrent»).

Страница с нулём торрентов — **валидный пустой baseline** (сериал только
анонсирован): запись создаётся, сообщение «На странице пока нет серий,
отслеживаем появление». Правило «0 торрентов = ошибка» действует только
в проверках после добавления. (Моё решение по обоим пунктам.)

### Проверка (`Monitor.check_release`, ветка `source='anistar'`)

1. Скачать и разобрать страницу. 0 торрентов при успешном HTTP → ошибка
   «не удалось разобрать страницу» (возможно, смена вёрстки).
2. Порог новизны: ранее невиданных id (нет в `known_torrents` вообще) > 15 →
   `error`, ничего не грабить.
3. Вычислить кандидатов по общей логике (см. выше), включая режим догона,
   если Sonarr привязан и пуст.
4. Нет кандидатов → статус `ok`, обновить `episodes`/`title` при изменении.
5. Есть кандидаты:
   - Скачанные в Sonarr серии (если библиотека Sonarr не пуста) пропускаются
     с записью в историю («Серия N уже скачана в Sonarr»).
     Нумерация на AniStar абсолютная («Серия 91»), поэтому для anistar-раздач
     сравнение идёт по `absoluteEpisodeNumber` **независимо от `seriesType`**
     в Sonarr: добавить параметр `force_absolute=True` в
     `SonarrClient.downloaded_episodes` (при пустом `absoluteEpisodeNumber`
     — fallback на `episodeNumber`, как сейчас). Иначе для сериалов с типом
     `standard`/`daily` сравнение было бы в чужом числовом пространстве
     (существующий код берёт абсолютную нумерацию только при
     `seriesType == 'anime'`). (Моё решение; проверь, что твои сериалы в
     Sonarr имеют заполненный `absoluteEpisodeNumber` — для аниме он
     заполняется автоматически.)
   - Для оставшихся: скачать `.torrent`
     (`GET /engine/gettorrent.php?id=<id>`, тот же UA; проверить
     content-type/префикс `d8:announce` — защита от HTML-страницы вместо
     торрента) и отправить в qBittorrent.
   - Категория: как в существующем потоке — `sonarr.download_category()`,
     если доступен (по желанию, не блокирует отправку).
6. Обновить `known_torrents` (обработанные id с флагами), `episodes`, статус
   `grabbed`, история по каждой отправленной серии (включая, какой торрент
   выбран при дедупликации: «многоголосая озвучка» / «без комментария, сиды X»).

Файловая дельта (приоритеты файлов) **не применяется**: один торрент = одна
серия, качается целиком.

### Отправка в qBittorrent

Новый метод `QbitClient.add_torrent(content: bytes, filename: str,
category: str | None)`: `POST /api/v2/torrents/add` multipart с полем
`torrents` (файл), опционально `category`. Напрямую через URL не добавляем —
qBittorrent ходил бы на сайт со своим UA и, вероятно, получил бы 403;
скачивать `.torrent` самим надёжнее. (Моё решение.)

Prowlarr для anistar-раздач не используется вообще: ни search, ни grab.

### Парсер (`app/anistar.py`)

- `is_anistar_url(url) -> bool` — хост.
- `parse_series_page(html: str) -> {"title": str, "torrents": [...]}` — чистая
  функция: разбиение по блокам через `re.split` по маркеру
  `id="torrent_(\d+)_info"`, извлечение подписи (`info_d1`), комментария,
  номера серии, размера, сидов, даты. Подпись разбирается как
  `Серия <N>[.дробь] <комментарий> (<размер>)`: дробная часть → `episode=None`;
  комментарий — текст между номером и размером (может быть пустым, может быть
  `Многоголосая озвучка` или `[Xelenum & Sati Akura]`). Кодировку декодирует
  вызывающий (bytes → cp1251 → str) до вызова парсера.
- Покрытие тестами на сохранённых HTML-фикстурах (шесть реальных страниц,
  обезличенные) — в стиле существующих тестов, без сети.

  скачан весь доступный список серий.
- Карточка раздачи: значок источника («AniStar» / «Prowlarr») рядом

- Диалог редактирования: `search_query` скрыт для anistar-раздач.

### Ошибки и граничные случаи

- Страница недоступна / HTTP-ошибка → статус `error`, история (как сейчас).
- Страница прочиталась, 0 торрентов → `error` «Страница разобрана, но
  торренты не найдены — возможно, изменилась вёрстка» (кроме случая
  валидного пустого baseline при добавлении).
- `.torrent` не скачался (не тот content-type) → ошибка по этой серии в
  историю, остальные серии обрабатываются; id остаётся `processed=false`,
  попытка повторится на следующей проверке. Раздача в `error` только если
  не удалось обработать всё.
- Повторная отправка защищена моделью: успешно обработанные id получают
  `processed=true` и больше не кандидаты.
- qBittorrent не настроен → при наличии кандидатов раздача в `error` с
  понятным сообщением (настройте qBittorrent), id не обрабатываются,
  попытка повторится.
- Частичный сбой догона (упала отправка 40-й серии из 90): обработанные
  помечены, неудачные останутся кандидатами, следующая проверка (или
  «Проверить сейчас») догонит остаток — пока Sonarr пуст, режим догона
  активен на каждой проверке.

## Проверка результата

- `.venv/bin/pytest -q` — существующие тесты зелёные + новые тесты парсера и
  anistar-потока: baseline без граба, режим догона (пустой Sonarr → все
  серии), новая серия → grab в фейковый qbit, пропуск скачанной в Sonarr,
  дедупликация с приоритетом «многоголос», дробная серия → `episode=None`,
  0 торрентов на проверке → error, порог новизны.
- Ручной прогон spike-скриптом против живого сайта перед финальным мержем —
  вручную владельцем или отдельным согласованием (тесты без сети).
